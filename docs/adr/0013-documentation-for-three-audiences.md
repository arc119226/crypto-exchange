# ADR-0013:文件分成三種讀者,而不是一種

- 狀態:已採納(Accepted)
- 日期:2026-09-09
- 相關:`docs/README.md`、`docs/system-overview.md`、`docs/changelog-by-phase.md`、`docs/guides/self-hosted-runner.md`、`docs/guides/self-hosted-runner-newcomer.md`;ADR-0010(介面語言與新手 README)、ADR-0012(CI 跑在自建 runner)

## 背景

ADR-0010 把 README 拆成新手版(繁體中文 + 英文)與工程師版,理由是「這個專案接下來要交給的人,比要接手程式的人多」。那個判斷是對的,但它只切了一刀,而實際上有**三種**讀者:

1. **不寫程式的人**——創辦人、投資人、業務。他們要知道這個產品在賣什麼、錢怎麼流、以後能不能擴充。他們**不會**執行任何指令。
2. **想動手跑一遍的人**——新手版 README 服務的對象。
3. **要改程式的工程師**——`docs/README.md` 服務的對象。

第一種讀者在此之前**完全沒有對應的文件**。而且他們最容易被既有文件誤導:`docs/README.md` 的開頭是十二段密集的變更記錄,`plan-v1.0.md` 是 1,700 行的計畫書,兩份都會讓不寫程式的人得到「這東西很成熟、什麼都有」的錯誤印象。

同時發現三個具體問題:

- **`docs/README.md` 的前 40% 是變更記錄。** 一個剛打開這個 repo 的人,要先讀完 4a-1 到 5b 每個 Phase 抓到什麼 bug,才會看到「怎麼跑起來」。那些內容很有價值,但位置錯了。
- **沒有任何文件說明 CI 的七個 job 各在做什麼。** 唯一接近的是 `plan-v1.0.md` §13.3 的清單,而它是**寫在程式之前**的,已經和實際的 workflow 對不上(還是合併前的九個 job、有已經不存在的 job、`e2e` 寫錯 profile)。
- **`docs/guides/self-hosted-runner.md` 假設讀者是工程師**,而實際要照著做的人不一定是。

## 決定

### 1. 新增 `docs/system-overview.md`,給不寫程式的人

四個部分:七個角色的業務比喻與三種資料傳遞方式、兩個「說故事」的流程(充值到成交、提現到轉出)、CI 全綠在日常營運裡代表什麼、以及未來的擴充指南。

**零程式碼區塊。** 每個技術名詞第一次出現時,括號裡用一句日常生活的東西解釋。

**這份文件必須寫明六條邊界**,而且是列在最前面而不是藏在結尾:

| 事實 | 不能被寫成 |
|---|---|
| 只連得上 anvil 與 Sepolia,永遠不接主網、不碰真錢 | 「已經在託管真實資產」 |
| 一個部署只服務一條鏈 | 「支援多鏈」 |
| 單租戶(`tenant_id` 每張表都留了,但 ADR-0003 說 v1 單租戶) | 「多租戶 SaaS」 |
| 撮合引擎刻意是單一實例(Postgres advisory lock) | 「可水平擴充的撮合叢集」 |
| 外部流動性:程式碼完全不存在 | 「已支援外接流動性」 |
| 行銷活動:程式碼完全不存在 | 「內建行銷模組」 |

**這一條是這份 ADR 的重點。** 一份給投資人看的文件,誠實不是道德要求而是工程要求——因為讀它的人會據此做承諾,而承諾兌現不了的成本由工程團隊承擔。後兩項寫成「**接頭已經留好,東西還沒做**」,並說明各自缺什麼(外部流動性缺的是庫存的會計科目,行銷缺的是活動資料表與專屬費用科目)。這比含糊帶過更有說服力,因為它可以驗證。

### 2. 變更記錄搬到 `docs/changelog-by-phase.md`,一字不改

`docs/README.md` 開頭那十二段搬過去,原文保留。它記的是每個 Phase 抓到什麼真缺陷、怎麼修的——**這是這個專案最有價值的資產之一**,不能刪,但它是變更記錄,不是入口。

`docs/README.md` 的「目前進度」用三句話帶過,連過去。

### 3. `docs/README.md` 重寫:語氣與深度都放低

不只是排版。使用者的要求是「改成新手版那種有耐心的說話方式」,而且技術深度也要降——假設讀者是工程師,但**不假設他熟悉這個專案**。

具體:新增一節「五分鐘看懂它怎麼組起來」(七個角色 + 三條通訊路徑),這是理解其他所有段落的前提而先前完全缺席;把塞滿行末註解的巨大 `sh` 區塊拆成十個有標題的步驟,說明放區塊外(ADR-0010 §5 的既有家規);repo 樹狀圖改成表格;17 列文件索引分成五組。

### 4. runner 文件拆成兩份,不是一份寫給所有人

- `docs/guides/self-hosted-runner.md` **就地升級**成正式的工程師版:補上「為什麼釘 24.04」在安裝當下就說(理由原本在 280 行之後)、`wsl -l -o` 與 `--unregister` 與手動開 Windows 功能的退路、與既有發行版共存,並新增**第 12 節「CI 會跑哪些 job,每個 job 在證明什麼」**。
- `docs/guides/self-hosted-runner-newcomer.md` 是新的高中生版,沿用 ADR-0010 已經決定的七段骨架,**每一步都有「你會看到:」**。

第 12 節同時解決了上面「沒有文件說明 CI 在做什麼」的問題,而且放在 runner 文件裡是刻意的:**前面每一項機器設定,都是為了某一個 job 存在的**,兩件事放在一起才看得懂為什麼要裝 gcc、為什麼要調 inotify。該節結尾有一張「你在第幾節做的事 → 是為了哪個 job」的對照表。

### 5. `plan-v1.0.md` §13.3 不再維護第二份 job 清單

改成指向第 12 節,只留下**不會隨 job 重組而變的性質**(每個 job 都要有 timeout、版本釘住、失敗語料進版控、`runs-on` 必須是變數、純文件 PR 的 path filter 與它的後果)。

計畫文件寫在程式之前,讓它描述實作細節就一定會腐爛。這次是實例:那份清單裡有三個已經不存在的 job,而沒有人發現。

## 後果

- **三份 README 的測試(`test/docs/readme_test.go`)只守三個檔案**,新文件不受它約束。但只要被三份 README 之一引用(連結或反引號路徑),路徑就必須正確——這次新增的四份都被 `docs/README.md` 引用,所以受測。
- **`README.md` 與 `README.en.md` 這次完全沒動。** 動了就要兩邊同步(`##` 數量相同、程式碼區塊逐一 byte 相同、圖片同序),那是另一次改動的範圍。
- **文件數量增加了。** 代價是維護面變大;換到的是每一種讀者都有一個正確的入口,而不是共用一個對誰都不夠好的入口。判斷依據和 ADR-0010 同一條:讀的人比寫的人多。
- **六條邊界會過期。** 接了第二條鏈、做了流動性模組之後,`system-overview.md` 的第一張表要跟著改。它是刻意放在最前面的,不容易漏掉。
- **`system-overview.md` 沒有測試守著。** 它宣稱的事實(單鏈、單租戶、不接主網)如果和程式碼漂移了,沒有東西會報錯。目前靠 review;真的成為問題的話,可以像 runbook 那樣加一支測試斷言關鍵字。
- **第 12 節會和 `ci.yml` 漂移。** 它記的秒數是一次量測,job 重組之後會不準。秒數本來就標明是「這台機器上量到的」,而結構性的描述(每個 job 在證明什麼)變動得慢。
