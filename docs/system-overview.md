## 先講清楚這套系統現在是什麼、還不是什麼

這是一份工程文件,不是簡報。所以在講它多好之前,先把界線劃清楚——**下面這六件事寫錯了,就等於對人失真**:

| 事實 | 不能說成 |
|---|---|
| 這套系統**只連得上測試用的區塊鏈**(一個跑在自己電腦裡的假鏈,和以太坊官方的測試網 Sepolia)。**它永遠不會連上主網,也不會碰到一塊錢真錢。** | 「已經在託管真實資產」 |
| 一次部署**只服務一條區塊鏈** | 「支援多鏈」 |
| 目前是**單一客戶**的形態。每一張資料表都預留了客戶編號的欄位,但多客戶共用一套系統是下一個版本的事 | 「多租戶 SaaS」 |
| 撮合引擎**刻意設計成只有一個實例**。它靠資料庫的一把鎖保證全世界只有一個在跑 | 「可以橫向擴充的撮合叢集」 |
| **外接其他交易所的流動性:這個功能還不存在。** 一行程式碼都沒有 | 「已支援外接流動性」 |
| **行銷活動模組:也還不存在。** 沒有推薦碼、沒有活動、沒有返佣 | 「內建行銷模組」 |

要跨過第一條線——也就是真的接主網、真的碰真錢——需要通過一份寫好的檢查清單([`plan-v1.0.md`](plan-v1.0.md) §22)。那是刻意設計的閘門,不是還沒做完。

最後兩項在第四節會講清楚:**接頭已經留好了,東西還沒做**,而且我會說明各自缺什麼。這比含糊帶過更有用,因為它可以驗證。

## 一、系統架構:把它想成一家銀行加一個交易大廳

一家真的交易所,螢幕後面其實是好幾個完全不同的工作。這套系統把它們分成**七個角色**,每個角色像公司裡的一個部門。

技術上,七個角色是**同一個執行檔**(一個安裝好就能跑的程式),啟動的時候用一個參數決定它今天扮演誰。小規模的時候七個可以擠在一台機器上;長大了就一個角色一台機器,**程式碼一行都不用改**。這種做法叫「模組化單體」——像一棟隔間可拆的房子,而不是七棟蓋死的獨立建築。

### 七個部門

**櫃台(api)**——對外唯一的窗口。客戶開戶、查餘額、要一個充值地址、下單、送出提現申請,全部經過它。

櫃台最重要的特徵是**它的權限小得驚人**:它不能改訂單簿、不能鎖住任何人的錢、不能簽名,連提現那張單它都只能「建立」不能「修改」——這是資料庫層級的權限設定,不是靠程式自律。理由很簡單:對外的窗口是最可能被攻破的地方,所以它手上不該有任何值錢的東西。

**撮合員(engine)**——交易大廳中央那個人。全場**只有他**能動訂單簿(order book,就是「誰想用多少錢買多少、誰想賣」的那張排隊表)。

每個市場(例如 ETH 換 USDC)有一條專屬的處理線,單子按照「價格優先、同價格先到先贏」排隊。整個系統靠資料庫的一把鎖保證**同時只會有一個撮合員存在**——這是刻意的。兩個撮合員同時改同一張表,是交易所最典型的災難來源。

**金庫管理員(chain)**——負責區塊鏈上的一切,但**不碰鑰匙**。他做五件事,各自獨立地循環:盯著鏈上有沒有錢匯進來、把該出去的錢送出去、把散在各處的錢收回金庫、每隔一陣子去數一次帳、以及補油錢。

**鑰匙保管人(signer)**——**全公司唯一拿得到金鑰的人,而且他從不出門**。

這個角色沒有任何對外的門,只從公司內部的對講機接工作,而且他只接受一種指令格式:「請幫我簽『第 123 號提現,第 0 次嘗試,轉 X 元到 Y 地址』這個**意圖**」。

注意這裡的細節:他收到的是**意圖**,不是別人組好的交易。他自己根據資料庫裡的資料把交易組出來再簽。差別在哪?如果他簽的是別人遞過來的一包資料,他就得先解讀那包資料、再相信自己的解讀沒錯——而收款人地址是藏在一串十六進位裡的。自己組就沒有這個信任問題。

而且同一個意圖**只能被簽一次**,這是資料庫的唯一鍵在擋,不是靠程式記得。

**電子看板(stream)**——把發生的事即時推給所有人的瀏覽器。有人成交了、深度變了、你的餘額動了。斷線重連的時候它能從紀錄裡把你漏掉的補回來。

**後台辦公室(admin)**——內部人員用的。改手續費、審提現、看報表、調帳。

它同樣被刻意削權:**它沒有區塊鏈的連線,也沒有任何金鑰**。所以審核人員按下「批准這筆提現」的時候,系統實際上只是在資料庫裡寫下一個「請求」,真正動手的是金庫管理員。為什麼要這樣繞?因為一個能直接寫入「交易編號」的角色,可以讓一筆提現**看起來已經送出去了,但其實從來沒有被簽過**。

**郵務室(worker)**——沒有人在等它的那些工作:寄通知給客戶、把成交整理成 K 線圖、清掉太舊的資料。

### 這七個部門怎麼互相傳資料

三條路,用途完全不同。

**第一條:對講機。** 需要等回答的時候用。櫃台問撮合員「這張單你收不收」,然後站在那裡等。金庫管理員請鑰匙保管人「幫我簽這個」,也是等。

**第二條:布告欄。** 不需要等回答的時候用——「剛剛成交了一筆」「這筆充值確認了」。貼上去就走,誰想看誰去看。

布告欄的做法是這套系統**最重要的一個設計**,值得用一整段講。

一般人直覺的做法是:資料庫寫完,然後發一則通知。問題是這中間有個縫——如果資料庫寫成功了、發通知的時候程式當掉,那就變成「事情發生了,但全世界沒人知道」。反過來,如果先發通知再寫資料庫,就會變成「大家都收到通知了,但事情其實沒發生」。

這套系統的做法是:**通知不是「發」出去的,是跟業務資料寫在同一筆資料庫交易裡的**。你要記一筆成交,就在同一個動作裡把「成交了」這則消息也寫進資料庫的一張待發表。這兩件事要嘛一起成功,要嘛一起失敗,沒有中間狀態。然後有一個常駐的搬運工,把待發表上的東西搬到布告欄。

結果是兩個方向都關死了。而且就算搬運工重複搬了,每則消息都有一個唯一編號,收的人自己會去重。

**第三條:便利貼(Redis——一種把資料放在記憶體裡、讀寫極快但斷電就沒的資料庫)。** 用來記「這個人這一分鐘打了幾次 API」和「訂單簿現在長什麼樣」這類東西。**它永遠不是真相**,掉了就重算一次,系統的健康檢查甚至把它列為「壞了也不算故障」。

### 真相住在哪裡

只有一個地方:**Postgres 資料庫**(一種開源的關聯式資料庫)。布告欄只負責傳話,便利貼只是加速,兩個都可以整個清空重建。

這件事聽起來像廢話,但它是交易所最常出事的地方。一旦「錢的數字」有兩個來源,它們遲早會不一樣,而那一天沒有人知道該相信誰。

### 帳是怎麼記的

用**複式記帳**——就是會計已經用了五百年的那一套:每一筆錢的移動,一定同時記在兩個地方,一邊減一邊加,兩邊金額相等。

所以「把 1000 元從 A 移到 B」在系統裡不是「A 減 1000、B 加 1000」兩個動作,而是**一筆有兩條腿的分錄**,而且系統在兩個層次檢查它平不平:程式裡檢查一次,資料庫在交易提交的那一刻再檢查一次。任何一邊不平,整筆退回。

還有三件事值得知道:

- **帳本是唯讀往前加的。** 沒有任何角色有權限修改或刪除已經記下的分錄。記錯了就記一筆相反的沖銷,原本那筆永遠留著。
- **金額不用浮點數。** 電腦的浮點數算 0.1 加 0.2 會得到 0.30000000000000004。在錢上面這是不能接受的,所以整套系統用的是精確的十進位數字,而且**有一條 lint 規則在自動擋**——有人不小心在金錢路徑上用了浮點數,程式碼根本合併不進來。
- **每一筆都有冪等鍵。** 同一件事重送第二次,系統會認出來,回傳第一次的結果,而不是記第二筆。

## 二、錢與資料怎麼跑:兩個故事

### 故事一:儲值 → 下單買幣 → 撮合成功

**第 0 步,還沒有人來之前。** 鑰匙保管人平常就在做一件事:**預先造一批充值地址**放在池子裡。為什麼要預先?因為造地址需要用到金鑰,而櫃台沒有金鑰。先造好放著,櫃台要的時候直接撥一個給客戶,整條路上櫃台都碰不到鑰匙。

**第 1 步,客戶要一個充值地址。** 客戶在網頁上按「充值」,櫃台從池子裡撥一個沒人用過的地址給他,記下「這個地址屬於這個帳號」。

同一個客戶再按一次會拿到**同一個地址**;而且原生幣和所有代幣共用這一個地址。如果池子空了,櫃台會誠實回報「暫時沒有」,而不是隨便生一個。

**第 2 步,錢到了鏈上。** 金庫管理員每隔幾秒去區塊鏈上看一次:有沒有錢匯進我們的地址?

看到了之後,他先記一筆「**看到了**」。注意——**這時候還不是錢**。客戶的餘額一毛都沒有變。

為什麼?因為區塊鏈會「反悔」。剛上鏈的交易有機會在幾分鐘內被推翻(這叫 reorg,可以想成「銀行說這筆匯款先掛著,還沒真的入帳」)。所以系統要等後面再疊上幾個區塊才算數,而**要疊幾個是每個幣各自設定的**——不同的幣、不同的風險,不該用同一個數字。

**第 3 步,確認數夠了,這一刻才是錢。** 系統在**一筆資料庫交易**裡同時做完三件事:記一筆分錄(金庫的科目減、客戶的可用餘額加)、把那筆充值標記成已入帳、以及把「充值到帳了」寫進布告欄的待發表。

三件事一起成功或一起失敗。所以不會出現「客戶餘額加了但沒有紀錄」,也不會出現「通知發了但錢沒進來」。

消息上了布告欄之後,看板部門把它推到客戶的瀏覽器,郵務室把它寄給有訂閱的商戶。

**第 4 步,客戶下單買幣。** 客戶說「我要用 2000 的價格買 0.5 個 ETH」。

櫃台檢查完格式和權限,把這張單透過對講機交給撮合員。撮合員收到之後,在**一筆資料庫交易**裡依序做:

1. **先凍結錢。** 這張單總共要付 1000 USDC,所以先把客戶帳上的 1000 從「可用」搬到「凍結」。

   為什麼要凍結?因為如果不鎖,客戶可以一邊掛著單、一邊把錢領走,等到真的成交的時候他付不出來。**錢還是他的**,只是暫時不能動,撤單或成交之後就解開。

2. **跑撮合。** 這一段是純粹的計算——沒有資料庫、沒有網路、沒有時鐘、沒有亂數。同樣的一串指令重放一次,會得到一模一樣的訂單簿。這讓它可以被完整地測試,也讓引擎重啟之後能從紀錄裡把簿子原封不動地重建回來。

3. **成交的話,把結果記成一筆借貸相等的分錄。** 買方的凍結減、賣方的可用加、手續費進交易所的收入科目——全部在同一筆分錄裡,兩邊相等。

4. **把「成交了」「你的單成交了」「你的餘額變了」寫進待發表。**

**全部提交之後**,才回覆客戶「你的單收到了」。順序是刻意的:先確定資料庫存下來了,再告訴人。

**第 5 步,為什麼拿到的數字不是整數。** 假設 alice 早就掛了賣單,bob 來買。成交之後 alice 拿到的是 0.1998 而不是 0.2,bob 拿到的是 399.2 而不是 400。

因為交易所收手續費,而且**掛單方和吃單方費率不同**:alice 先把單掛在簿上、提供了流動性,算掛單方,收 0.1%;bob 來吃掉別人的單,算吃單方,收 0.2%。成交價永遠用**掛單方**的價格。

這就是交易所的主要收入,而且它是在成交的那一筆分錄裡直接記成收入科目的,不是事後結算。

### 故事二:申請提幣 → 錢包轉出

提現比充值危險得多——充值出錯是少收了錢,提現出錯是**錢真的不見了**。所以整條路徑被切成很多段,每一段之間都有一道確認。

狀態依序是:**送出申請 → 政策檢查 → 自動核准或待人工審核 → 核准 → 鎖定資金 → 已簽名 → 已廣播 → 已確認**。

**第 1 步,客戶送出申請。** 櫃台建立一張提現單,狀態是「送出申請」。

這裡有兩個設計值得注意。第一,**必須帶一個冪等鍵**——客戶自己給的一個編號。網路不穩重送第二次的時候,系統認得出來,回傳第一張單,而不是提兩次錢。如果同一個編號但內容不一樣,直接拒絕。

第二,**櫃台從此不能再碰這張單**。它連修改的權限都沒有(資料庫層級)。

**第 2 步,政策檢查。** 金庫管理員拿這張單去對規則:這個帳戶被凍結了嗎?這個幣開放提現嗎?金額夠不夠最小值?這個客戶的身分驗證等級能提多少?他過去 24 小時已經提了多少?

結果只有三種:**自動核准**、**待人工審核**、**拒絕**。

一個重要的取捨:**超過額度是進人工審核,不是拒絕**。因為一個大額提現的正確處理方式是「有人看一眼」,不是「叫客戶自己想辦法」。

**第 3 步,人看一眼。** 待審的單子進後台的佇列。審核人員按核准或拒絕。

再強調一次:**後台只能改狀態**。它沒有節點也沒有鑰匙,不可能自己把錢送出去。

**第 4 步,鎖定資金。** 金庫管理員把客戶的錢從「可用」搬到「凍結」,同時把單子改成「已鎖定」——同一筆交易。

**這一步一定要先於簽名,而且沒有例外。** 如果先簽了名再鎖錢,中間那個瞬間客戶可以把錢領走,結果就是簽出去的交易沒有對應的資金。

**第 5 步,簽名。** 金庫管理員先算手續費(gas,可以想成「郵資」)。如果現在的郵資超過設定的上限,**這張單就在這裡等**——不是失敗,是等,等到郵資回到合理範圍。

然後他先把序號(nonce,可以想成「這個錢包送出的第幾封信」)固定下來並存進資料庫,**才**去請鑰匙保管人簽名。順序也是刻意的:先存序號,程式當掉重開之後才知道自己上次用到哪。

鑰匙保管人簽完,把結果記進一張「簽名紀錄表」,那張表的唯一鍵保證**同一個意圖不可能被簽第二次**。

**第 6 步,廣播。** 把簽好的交易送上區塊鏈,然後在一筆資料庫交易裡把客戶的凍結款搬到「待處理提現」這個科目。

如果區塊鏈拒收,系統會**先去鏈上確認這個序號真的沒被用掉**,確定沒有才把錢退回客戶的可用餘額。這個檢查很重要——沒有它,一個「送出成功但回應遺失」的狀況會導致錢既送出去了又退回來。

**第 7 步,追蹤與確認。** 系統盯著這筆交易上鏈了沒。太久沒動就**用同一個序號、更高的郵資重送一次**,最多重送幾次是設定的。重送次數用完還沒動,它會停下來讓人處理——這比無限重試好,因為無限重試會把郵資燒光而且沒人發現。

確認之後記**兩筆**分錄,不是一筆。因為提出去的幣和付掉的郵資**是兩種不同的幣**,一筆分錄裝不下。

**第 8 步,萬一鏈上失敗了。** 交易上鏈但執行失敗的話,郵資照樣被扣掉(這是區塊鏈的規則,沒得商量),但**那筆錢會刻意停在「待處理提現」科目等人來看**,不會自動退給客戶。

因為自動退款需要百分之百確定錢真的沒出去,而這種情況下系統沒有那個把握。**寧可讓人看一眼,不要自動做錯。**

## 三、CI/CD 全綠代表什麼

### 先講它實際上做了什麼

「CI/CD」是「持續整合 / 持續交付」——白話說就是:**每次有人改一行程式,一台機器會自動把整套東西從零檢查一遍**。

在這個專案裡,那「一遍」大概是 25 分鐘,內容是:

從一台什麼都沒有的機器開始,把整座交易所蓋起來——資料庫、訊息佇列、一條假的區塊鏈、七個角色各一個容器。然後在那條假鏈上真的匯錢進來、等確認、真的下單、真的成交、真的提現出去、把散落的錢歸集、跟鏈上對一次帳。接著打開一個瀏覽器,像真人一樣註冊帳號、入金、掛單、看它成交。再來備份一次資料庫、還原到另一個資料庫、驗證還原出來的帳是平的。

中間還會**故意把撮合引擎砍掉**(直接 kill,不是好好關機),然後看它重開之後訂單簿是不是一分不差地回來。

最後把整套東西裝進一個迷你的 Kubernetes 叢集(一種管很多台伺服器的系統)再跑一次,**在那裡也故意砍一次引擎**。

全綠代表這 25 分鐘裡沒有任何一項出錯。

### 它幫你省了什麼麻煩

**不必養人手動測。** 上面那 24 個步驟,以前要靠人照著清單點一遍,一次半小時起跳,而且人會漏。現在每次改程式都全跑一遍,而且不會累。

**不必怕改壞不知道。** 有幾類錯誤是**結構性地不可能溜過去**的:帳本借貸不相等、餘額變成負數、金額用到浮點數、金鑰印進 log、產生的程式碼跟規格對不上、跨層的引用違反架構規則——任何一項都會讓紅燈亮,而且是在合併之前。

**不必等到上線才發現部署設定寫錯。** 每一次都真的把整套東西裝進 Kubernetes 再拆掉。設定檔打錯字這種事,在 CI 就會被抓到,不是在上線那天半夜。

**發布不會手滑。** 版本號、映像檔、部署套件三邊對不上就不給發。

**改基礎設施的成本降到接近零。** 這件事很少被提到但很重要:開發者的筆電上沒有 Docker,所以那些牽涉到十幾個容器的改動,他**只能靠 CI 驗證**。CI 快而且免費,直接決定了這類改動願不願意做。

### 七道關卡各自在擋什麼

CI 分成七個獨立的工作,順序是刻意排的——**最便宜、最容易失敗的先跑**,這樣壞掉的改動幾秒就被擋下來,不會先燒掉二十分鐘。

| 工作 | 它在證明什麼 |
|---|---|
| **checks** | 二十一項靜態檢查與單元測試:程式碼風格、架構分層規則、**整個 git 歷史裡沒有洩漏過金鑰**、產生的程式碼跟規格一致、金錢模組的測試覆蓋率不低於 95%、兩個執行檔跑得起來、前台編譯得過、智能合約測試通過 |
| **fuzz-smoke** | 對撮合引擎丟 30 秒的隨機亂數,看它會不會崩。只在合併之後跑 |
| **integration** | 起真的資料庫和訊息佇列,測帳本、後台 API、撮合引擎、事件搬運 |
| **e2e** | **唯一驗證「拆開部署」的一關**:七個角色各一個容器,每一筆下單都必須真的走過對講機。上面那 24 個步驟就在這裡 |
| **helm** | 在迷你 Kubernetes 裡真的裝一次、跑一次、砍一次引擎 |
| **image** | 三個映像檔都 build 得起來**而且真的能跑**:執行檔印得出版本、網頁伺服器設定檔通過驗證、前台的靜態檔真的烤進去了、備份工具真的在裡面 |
| **release** | 只在正式發版的時候跑。版本號三邊一致才給發 |

### 誠實的一段:綠燈不代表沒有 bug

綠燈代表的是:**我們已知的每一種壞法,都已經自動試過一次了。**

而這份清單是**會長的**。舉一個真實的例子:對帳功能上線的第一天就抓到一個漏洞——交易所墊給充值地址的那筆郵資,在區塊鏈上看起來就是一筆「有錢匯進我們的地址」,於是掃描器把它當成客戶的充值入帳了。客戶白得一筆交易所墊的錢,而金庫的帳為同一筆移動記了兩次。

這個 bug **撐過了完整的整合測試和兩輪端對端測試**,直到有東西真的拿帳本去跟區塊鏈對了一次才現形。

修好之後,那個情境就永遠留在自動測試裡了。這比宣稱「零缺陷」有說服力得多:**它承認測試只能涵蓋想得到的情況,然後把每一次想不到的情況變成下一次想得到的**。

### 順帶一提:這件事現在是免費的

CI 原本跑在 GitHub 的機器上,而私有專案是按分鐘計費的。實際量過:這個專案一個月會用掉方案額度的 **7.8 倍**。

現在它跑在一台自己的閒置電腦上,**每個月的帳單是零**,而且比原本更快(25 分鐘,原本是 45 個計費分鐘)。做法與代價記在 [`adr/0012-ci-on-a-self-hosted-runner.md`](adr/0012-ci-on-a-self-hosted-runner.md),裝機步驟在 [`guides/self-hosted-runner.md`](guides/self-hosted-runner.md)。

## 四、改裝指南:以後想加東西的話

四個常見的需求,由易到難。每一個都寫:**要動什麼、有多難、缺什麼**。

### (一)上架一個新的代幣——純設定,不用改程式

在後台按「新增資產」,填幣別代號、合約地址、小數位數、要幾個確認數、最小充值與提現金額、歸集門檻。

按下去之後,系統會發一則「資產更新了」的消息,撮合引擎收到之後**自己重新載入設定,不需要重啟**。掃描器下一輪就開始看那個合約,歸集、提現、對帳三個模組也全部自動認得它。

然後再開對應的交易對、設定各身分等級的提現額度。

不透過後台的話,設定檔也可以放在版控裡按環境套用——目前有兩份現成的範例(本機假鏈一份、Sepolia 測試網一份)。

**難度:一杯咖啡。**

### (二)給量化交易者的 API——最容易的一個

這是四個裡面**現成程度最高**的,因為需要的東西幾乎都已經在了:

- **規格先行。** 有一份 API 規格文件是唯一的來源,伺服器程式碼、命令列工具、前台的型別定義**三份都是從它自動產生的**。要加端點就改那份規格再重新產生,三邊不可能對不上。
- **權限已經分好了。** API 金鑰本來就帶「範圍」(只能讀 / 可以交易),金鑰本身在資料庫裡是加密存放的。
- **限流可以按介面分別設定。** 給量化的端點單獨設一個更寬的額度,是加一行設定。
- **批次下單的引擎端入口已經寫好了。** 引擎裡有一個「一次收一批命令」的進入點,它的註解就寫著「批次端點也可以用這個」。要補的只是把它接到對外的 API。
- **即時推播的規格也有了**,加一個頻道是在一個既有的分支上加一個選項。

要做 FIX 或 gRPC(兩種機構客戶常用的協定)的話,是新增一個角色放在櫃台旁邊,底下重用完全相同的邏輯。

**難度:數週,而且風險低——因為不用碰帳本和撮合。**

### (三)行銷活動(送幣、手續費優惠)——記帳的縫已經有了

**送幣**這件事,帳要怎麼記已經解決了:系統有一個「調整帳務」的功能,從一個叫「外部」的科目撥錢到客戶的可用餘額,**強制填寫理由**,而且在同一筆交易裡寫一筆稽核紀錄。後台已經有這個端點,開發用的水龍頭就是走它。

**手續費優惠**連新程式都不用寫:費率表本來就是按市場設定、可以熱替換、而且有生效時間欄位。

**觸發條件**要接的東西也現成:「客戶完成身分驗證」「充值到帳」「成交了」這些消息本來就在布告欄上,寫一個訂閱者去聽就好,而且已經有一個現成的範例可以照抄。

**缺的是:** 活動本身的資料表(哪個活動、誰參加了、發過了沒)、一個專屬的「行銷費用」科目(現在會記到「外部」科目,那會跟營運人員的手動調帳混在一起,月底分不出來),以及後台的操作介面。

**難度:數週。真正的工在資料模型,不在管線。**

### (四)外接其他交易所的流動性——最沒有驗證的一個

**先說清楚:這個功能今天完全不存在。** 我搜過整個程式碼庫,沒有任何「場外報價」「造市」「對沖」相關的東西。

但形狀是清楚的。撮合引擎對外只暴露一個**只有三個方法的介面**(下單、撤單、查深度),而且這個介面**已經有兩種實作**——一種是同一個程式裡直接呼叫,一種是跨機器透過對講機。流動性提供者就是這個介面的第三個使用者:一個持有帳戶的程式,聽著布告欄上的成交消息,回頭掛出報價。

而且已經有一個東西證明這條路走得通:壓力測試工具就是一個自動下單的程式,它跑在完全相同的介面上。

**真正的工在帳,不在管線。** 庫存放在別的交易所,那筆錢在自己的帳本上該記在哪個科目?今天沒有這個科目。這是要先想清楚的事,而且想錯了會在半年後變成對不上的帳。

**難度:數月,而且是四個裡面唯一需要先做設計的。**

### (五)加一條新的區塊鏈——要工,但接頭留好了

鏈上的四件事(掃描、提現、歸集、對帳)**各自定義了自己的一個很窄的介面**,而不是共用一個大介面。簽名也在自己的介面後面。資料表裡早就有「鏈編號」這個欄位。

所以換一條 EVM 相容鏈(和以太坊同規格的鏈)主要是設定。

**但今天一個部署只服務一條鏈**,這是真的限制。要同時服務兩條,需要把設定改成清單、每條鏈跑一組工作、並且**把金庫科目按鏈拆開**——最後這項是資料庫的變更,程式碼裡的註解自己就寫明了這一點。

換成完全不同架構的鏈(比如比特幣那種)會更麻煩:地址格式在幾個地方是寫死成以太坊形狀的。

**難度:同規格的鏈數週,不同架構的鏈數月。**

### 憑什麼說這個架構好擴充

這種話很容易講,所以底下**不用形容詞,只用可以驗證的事實**:

**一、每一個「外面的世界」都藏在一個很窄的介面後面。** 區塊鏈有四個(而且是刻意分成四個,不是一個大的),簽名有一個,撮合有一個(三個方法)。這不是事後補的抽象層——它們的註解寫明了為什麼要這樣切:因為「確認數、鏈重組、收據」這些邏輯最容易寫錯,所以必須能用一條**假的、腳本控制的鏈**去測試每一種詭異情況。

**二、對外的契約是機器在檢查的,不是靠人記得。** 一份 API 規格產生三份程式碼;每一種事件都有一份格式定義和一份標準範例。任何一邊改了另一邊沒跟上,**建置直接失敗**。

**三、架構分層是 linter 在守的。** 領域邏輯不准引用訊息佇列;管地址的模組不准引用管金鑰的模組;金錢路徑上不准出現浮點數。這些是自動化規則,違反了程式碼合併不進來。**架構規則寫在文件裡會腐爛,寫成工具不會。**

**四、最強的證據:已經真的搬過一次了。** 鑰匙保管人原本跟其他角色住在同一個程式裡,後來搬到另一台機器上獨立執行。**呼叫端一行程式碼都沒有改**,因為中間隔著介面。

這不是「設計的時候說它會好搬」,這是**已經搬過,而且沒有留下疤痕**。
